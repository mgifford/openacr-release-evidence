# Evidence model v0.2

This model separates **collected source evidence**, **release applicability**
and **conformance**. Only the first two are implemented. Conformance remains a
human decision.

## Pipeline artifacts

| Artifact | Produced by | Purpose |
| --- | --- | --- |
| Collection | `acr-evidence collect` | Normalized issues, comments, MR metadata and provenance for one target. |
| Analysis | `acr-evidence analyze` | Release-specific applicability findings and commit/tag evidence. |
| Report | `acr-evidence report` | Static HTML/JSON draft for one target; never an ACR. |
| OpenACR draft | `acr-evidence openacr-export` | Schema- and catalog-valid OpenACR skeleton with no adherence values. |
| ATAG evidence | `acr-evidence atag-report` | ATAG 2.0 Part A/B evidence and WAI ATAG Report Tool JSON draft; no ATAG conformance values. |
| ACR narrative | generated by `multi`/`report` | Human-readable ACR draft; every criterion `Not Evaluated`. |
| Multi-target report | `acr-evidence multi` | One report per declared target plus a landing page and cross-release matrix. |
| Private raw snapshot | collection, under `private-evidence/raw/` | Original CLI/API payloads, excluded from publication. |

All public artifacts carry `schema_version`, `artifact_type`, `disclaimer`,
`generated_at`, `manifest_digest`, `digest_scope` and `evidence_digest`.

### Digest rules

- `evidence_digest` is the SHA-256 of the **published artifact** after removing
  `generated_at` and `evidence_digest`. It is reproducible from the published
  JSON alone.
- `manifest_digest` is the SHA-256 of the complete input manifest, including
  `applicability_overrides`. It is an input reference; the manifest itself may
  live in a private review repository.
- No digest is a conformance statement.

## Assessment target

```json
{
  "id": "drupal-core-11.4.12-default-admin",
  "product": "Drupal Core",
  "release": "11.4.12",
  "ref": "11.4.12",
  "synthetic": false,
  "components": ["Admin theme", "language system", "text.module", "core"],
  "standards": ["WCAG 2.2 AA", "Section 508 (revised, 2017)"],
  "installation": {
    "drupal_core_version": "11.4.12",
    "composer_lock_sha256": "…",
    "profile": "standard",
    "enabled_modules": ["…"],
    "enabled_themes": {"default": "olivero", "admin": "default_admin"},
    "configuration": "Declared site-builder configuration, not the stock profile default."
  }
}
```

`id`, `product`, `release` and `ref` must identify a real target. Values containing
`TEMPLATE`, `SET-A-REAL`, `SET-EXACT`, `EXAMPLE`, `UNVERIFIED`, `TODO`,
`CHANGEME` or `REPLACE-ME` are rejected unless `"synthetic": true` is explicit.
A synthetic artifact must never be presented as evidence about a real release.

must escape them; `description_text` is a derived, script-free text view. The
normalized public artifact does not include raw upstream payloads.

### Verified Drupal status map

The current Drupal.org queue does **not** use the old “8 = closed fixed”
assumption. Values verified against live issue pages on 2026-11-07:

| Code | Label | Workflow state |
| --- | --- | --- |
| 1 | Active | `open` |
| 2 | Fixed | `fixed-unverified` |
| 3 | Closed (duplicate) | `closed-other` |
| 4 | Postponed | `postponed` |
| 5 | Closed (won't fix) | `closed-other` |
| 6 | Closed (works as designed) | `closed-other` |
| 7 | Closed (fixed) | `closed-fixed` |
| 8 | Needs review | `needs-review` |
| 13 | Needs work | `needs-work` |
| 14 | Reviewed & tested by the community | `rtbc` |
| 15 | Patch (to be ported) | `patch` |
| 16 | Postponed (maintainer needs more info) | `postponed` |
| 17 | Closed (outdated) | `closed-other` |
| 18 | Closed (cannot reproduce) | `closed-other` |

Unlisted codes remain `Unknown status (N)`; do not guess from an older map.

### WCAG candidate tags

Issues may carry tags such as `wcag143`, `wcag1411` or `wcag253`. These are
parsed deterministically into `1.4.3`, `1.4.11` and `2.5.3`. There is no text
mining and no model mapping here. A tag is a candidate relevance signal, not a
conformance result.

## Issue cache and incremental discovery

`reports/collection.json` is both the public normalized evidence collection and
the issue cache. The weekly collector passes the committed collection as
`--previous-collection`. It pages the queue sorted by changed and stops once the
previous high-water mark is reached, reusing unchanged issues. Changed nodes are
re-fetched; nodes no longer in an active status are removed from the cache. The
manifest digest must match or the cache is ignored and a full discovery runs.

Inventory-only issues have only their node metadata/status to compare; full
comments and MRs are collected for the detailed subset. A change to comments,
MRs, status, description, metadata or evidence detail invalidates an issue's
cached evidence when the changed node is fetched.

## ACR review scope and discovery

ACR evidence includes only issues that still need review: Drupal status **1**
(Active), **8** (Needs review), **13** (Needs work), **14** (RTBC) and **15**
(Patch). Status **2** (Fixed), the closed statuses (3, 5, 6, 7, 17, 18) and the
postponed statuses (4, 16) are excluded. An RTBC issue stays in until it is
closed.

Discovery pages the full filtered issue queue (50 per API page, up to 200 pages)
instead of taking the first page. All active issues are included as normalised
inventory records. A review-priority subset is fetched with full comments, merge
requests and commit analysis; the rest are marked `evidence_status: inventory`
and `metadata-only` in the report. Inventory records are not assigned a release
applicability conclusion.

## Applicability states

| State | Meaning in this project |
| --- | --- |
| `confirmed-affected` | A reproduction on the target release demonstrates the barrier. Not emitted by the automated pipeline in this phase. |
| `likely-affected` | Report evidence suggests the barrier is present; it was not reproduced. |
| `confirmed-fixed` | A fix commit is contained in the target tag **or** branch **and** the tracker is closed fixed. Behavioural verification is still required; the finding is unreviewed. For a branch target this is a development-branch result, not a release claim. |
| `not-introduced` | The affected feature or code is absent from the target release. Requires code/feature evidence, not absence of reports. |
| `not-in-scope` | The component is outside the declared assessment scope. |
| `unknown` | Insufficient target-specific evidence. This is the safe default. |

Every finding carries `assessment_id`, `target`, `observed_at`,
`observed_at_basis`, `basis`, `reason`, `evidence_urls`, `review_status`,
`fix_included_in_target`, `fix_included_in_release`, and a `commits` list.
`fix_included_in_target` is the authoritative code-inclusion signal for both tag
and branch targets. `fix_included_in_release` remains true only for tag targets
and is retained for compatibility; it is false for a development-branch target.
Code inclusion is never the same as a verified behavioural fix.

### Classification rules (implemented)

1. Component outside the manifest → `not-in-scope`.
2. Explicit feature/code-absence evidence → `not-introduced`.
3. A matching fix commit contained in the target tag and a closed-fixed tracker
   → `confirmed-fixed` (with an explicit behavioural-verification caveat).
4. Matching commits exist but none is in the tag → `likely-affected`.
5. Closed-fixed tracker with no matching commit → `unknown`.
6. Open report created after the release date with no target-branch fix →
   `unknown` (it may be a later regression).
7. Open report before the release with no matching commit → `likely-affected`.
8. Closed non-fix or postponed with no matching fix → `unknown`.
9. A fix contained in a development branch does not establish release
   applicability; branch targets are labelled as development results.

## Multi-target policy

`config/drupal-core-targets.json` declares the supported, pre-release and
development targets. Each target supplies:

- a manifest path and ref (`tag` or `branch`);
- `release_line` and `support_status` (`supported`, `pre-release`,
  `development`, `eol`);
- an explicit branch set for commit indexing (never mix major-version branches
  implicitly);
- an optional `parent_project` and a target `scope_note`.

At this snapshot the policy declares two supported lines (10.6.x and 11.4.x),
two 12.0.x pre-releases and `main` as development. Support labels are policy
metadata, not release guarantees. The landing page records the policy note and
source URL.

The shared issue collection is target-independent. Each target analysis is
separate, so an issue remains visible across release lines until it is closed
(fixed or outdated) or ruled out with target-specific evidence. The
cross-release matrix links every cell back to the target finding.

`parent_project` is reserved for the project graph: Drupal Core is top-level;
Claro, Olivero, Drupal CMS and LocalGov Drupal can publish their own ACRs with a
parent link to Core. Parent-linked ACR generation is not implemented yet.

## Published evidence and ACR narrative

`evidence.json` is a compact public artifact containing findings and issue
identity; comments and descriptions are rendered in `index.html` from the full
collection and are not duplicated in the JSON. The committed analysis artifact is
no longer produced by `multi`; this keeps the report set small.

`acr.html`/`acr.md` convert the active evidence into an ACR narrative.
They describe issue counts and evidence states but assign no term; every criterion
is `Not Evaluated` until a reviewer completes it. The narrative is not a
conformance claim and does not inherit ATAG or OpenACR results.

## ATAG evidence

ATAG 2.0 is separate from WCAG/OpenACR. Issues tagged `atag` (Drupal term 5050)
carry an `atag` object with explicit Part A/B tags, curated scope, component
candidates and a `needs-triage`/`unreviewed` status. The ATAG report groups Part
A/Part B explicit and candidate issues, flags ATAG issues missing the common
Accessibility tag, and writes a WAI ATAG Report Tool JSON with all 63 criteria
`Not checked`. Component candidates are triage hints, not conformance. ATAG and
WCAG conclusions are never inherited from each other.

## OpenACR draft

`openacr.yaml` is validated against the pinned Civicactions/GSA OpenACR 0.1.0
schema and the OpenACR 2.5 WCAG 2.2 + Section 508 catalog. It lists all 182 catalog
criteria and all seven chapters, but **no components or adherence values**.
`draft: true`, a placeholder reviewer and notes force human review. A reviewer
must replace the author, assess every criterion, populate adherence, set
`draft: false`, and run `openacr-validate --strict`. `not-evaluated` is rejected
for Level A/AA by policy. The YAML has not been round-tripped through the official
editor; that remains a separate verification step. ATAG evidence is linked from
the draft notes and is not serialized into OpenACR WCAG criteria.

## Conformance (not implemented)

Conformance is a separate, human-reviewed decision for each applicable
requirement and target. It must not be derived from issue counts, issue status,
commit inclusion, automated checks or model output. No artifact in this
repository currently contains a WCAG conformance decision.

## Weekly digest

`weekly-summary` compares the current active collection with the previous
snapshot and writes immutable `reports/weekly/<date>.facts.json`,
`<date>.md` and `<date>.provenance.json`, plus an `index.md` trend table. Facts are
deterministic. Activity is detected from `updated_at`, status, comments, merge
requests, description/metadata and evidence-detail changes; only `activity.changed`
issues, new/no-longer-active issues and aggregate context are sent to the model.
If no issue changed, the model is not called. The output is validated against the
facts and falls back to the deterministic digest on rejection or failure. The
digest is not an ACR and does not change `openacr.yaml` or the ACR narrative.
