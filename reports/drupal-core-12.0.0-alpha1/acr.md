## Draft status and ACR result terms

ACR result terms are defined here so the draft uses the same vocabulary as a completed ACR. Results are proposed from the declared surface assessment and the known-barrier register; a reviewer must confirm every term and explanation.

**ACR result terms used in review**

| Term | Meaning |
| --- | --- |
| Supports | The product has at least one method of meeting the criterion, and the reviewer has evidence that it works for the evaluated scope. |
| Partially Supports | Some product functionality meets the criterion; other functionality does not, and the reviewer can explain the boundary. |
| Does Not Support | The majority of product functionality does not meet the criterion. |
| Not Applicable | The criterion is not relevant to the product, and the reviewer records why. |
| Not Evaluated | No active tagged issue and no other evidence supports a per-criterion term. Absence of a tagged issue is not evidence of support. |

## Scope and evaluation method

The evidence collection covers active, review-relevant Drupal Core Accessibility issues: Active, Needs review, Needs work, RTBC and Patch. Fixed, closed and postponed issues are excluded. The snapshot contains 432 active findings, of which 196 carry at least one explicit WCAG issue tag.

38 findings have full comments and merge-request evidence; 394 are metadata-only inventory records. The inventory records identify active issues but do not include comments, merge requests or commit analysis. All findings are unreviewed.

- Discovery pages the complete Accessibility queue; it does not stop at the first API page.
- WCAG tags are candidate relevance signals from the issue queue, not conformance determinations.
- No issue was reproduced against an installed Drupal target in this pass.
- Open issue reports are treated as draft barrier evidence; they are not a release reproduction.
- No keyboard, screen-reader, zoom, reduced-motion or forced-colors testing of the product is claimed.
- No AI was used to assign applicability or an ACR result.
- Automated coverage is partial: axe/ACT rule mappings show where some evaluation is possible, but no pass/fail result is recorded here. Guidepup can add behavioral screen-reader evidence when a run is recorded; no Guidepup run is claimed in this snapshot.

Theme availability for 12.0.x: front-end themes none recorded; admin themes default_admin. Removed in this line: olivero, claro. The core collection does not include the theme project queues; a theme's own ACR must cover those issues.

## How the draft results are assigned

The declared Drupal surface assessment is the baseline. Web and Authoring Tool are assessed surfaces. The active accessibility issue queue is the known-barrier register for those surfaces.

A known active issue on a surface produces Partially Supports. An assessed surface with no active tagged issue produces Supports. Does Not Support is not recorded because there is no explicit broad-failure evidence. Not Applicable is used only for documented feature absence. Not Evaluated is reserved for an unassessed surface.

This is an issue-queue attestation, not a WCAG-EM audit. Supports does not mean that axe-core or any other automated tool proved the criterion; automated coverage is partial and is reported separately.

The media criteria 1.2.1, 1.2.3, 1.2.4, 1.2.5 and 1.4.2 are Not Applicable because Drupal Core does not provide the relevant audio/video player, live-media feature or automatic audio control. They are not Not Applicable because the queue is empty.

## Why this ACR is different

A VPAT is a template; a completed report is an ACR. Most vendor ACRs are periodic, sample-based snapshots reviewed by legal or product management, with the vendor's issue queue kept separate. This report is an issue-queue attestation: it is generated from the full active Drupal Core Accessibility queue and keeps every cited issue linked.

**Conventional vendor ACR and this issue-queue attestation**

| Dimension | Conventional vendor ACR | This ACR |
| --- | --- | --- |
| Cadence | Annual, biennial or procurement-driven | Every weekly tracker snapshot |
| Evidence | Selected pages, flows or a WCAG-EM sample | Full active Accessibility queue; comments/MRs where collected |
| Traceability | Summary claims, often without issue links | Every cited issue links to the public Drupal.org source |
| Authoring | Often folded into web or omitted | Explicit Authoring Tool component and separate remarks |
| Change | Static until the next report | Incremental; new issues and status changes appear next snapshot |
| Independence | Often a commissioned assessment | Community-reported issue evidence; no independent WCAG-EM audit |

It is stronger on completeness of known reports, traceability, recency and connection to the remediation backlog. It is weaker on independent page sampling and manual assistive-technology coverage. It is not a WCAG-EM evaluation, a certification or a substitute for a procurement-specific ACR. A missing tagged issue is not evidence of support.

Read the queue as reported barrier evidence. The criterion result is a draft issue-queue attestation subject to human confirmation. See the GSA OpenACR discussion and Drupal's ACR process for the wider model.
